# 도레미 — 주가 감시 사이트

https://gvyhuj.github.io/go-monitor/

한 종목의 주가가 **급등·급락**한 순간을 자동으로 기록하고, 왜 움직였는지를 찾아 웹사이트로 보여줍니다.
기사·공시 공개 전후 관측된 주가와 시장 움직임을 기록·비교합니다. 기사 인과 효과를 확정하지 않습니다.

- 서버나 PC 없이 GitHub에서 자동으로 돌아갑니다. 비용 0원.
- 분석 자료는 모두 암호화되어 있어, 사이트에 들어가야만 볼 수 있습니다.

```
GitHub Actions (장중 약 3분마다, 그 밖에는 약 15분마다)            GitHub Pages
  시세·뉴스 수집 → 급등·급락 감지 → 원인 분석 → 알림  ──▶  사이트 (자료는 암호화)
  기록은 암호화해서 다음 실행으로 넘김
```

## 무엇을 기록하나
| 단계 | 기준 | 알림 |
|---|---|---|
| 대형 | ±15% 이상 | 보냄 |
| 급등·급락 | ±10% 이상 | 보냄 |
| 관찰 | ±5~10% | 사이트에 기록만 |

기준 숫자는 `settings.json`(event_watch_pct · event_move_pct · event_big_pct). 상장 뒤 하루 등락 중간값이 약 4%라
±3%는 거래일 60% 이상, ±5%도 40% 가까이에서 일어나서, 상위 약 10%인 ±10%를 알림 기준으로 정함 (2026-10).

- 하루 기준: 종가가 전일 종가보다 위 기준 이상 움직인 날
- 장중 누적 기준: 장중에도 전일 종가 대비 위 기준 이상이 5분 이상 유지되면 바로 기록·알림
  (천천히 오래 빠지거나 오르는 날 대비. 장 마감 뒤 확정 종가로 갱신)
  전일 종가는 네이버 기준가(현재가 − 전일 대비)를 써서 배당락·권리락 날에도 네이버와 같은 숫자로 판단.
  관찰 기준(±5%) 안으로 5분 이상 회복하면 임시 기록을 지우고, 그 뒤 다시 기준을 넘으면 알림을 한 번 더 보냄
- 장중 기준: 30분 안에 위 기준 이상 움직이고, 그 가격이 5분 이상 유지
  (체결 한두 건으로 튄 가격은 제외)

## 원인은 직접 붙여넣기
사이트에는 숫자(몫 나누기·창구 매매·비교 종목·테마 등락·기사 목록)만 자동으로 싣고, 원인은 싣지 않습니다.
원인 분석 창의 'ChatGPT에게 묻기'(숫자·사실 자료만 채워 보냄)로 받은 답을 '원인 붙여넣기'로 넣으면,
암호화된 요청(GitHub 이슈)으로 올라가 다음 실행 때 반영됩니다. 하루 칸에 넣은 원인은 같은 날·같은 방향 장중 순간에도 보입니다.
아래 3단계는 숫자를 계산하는 방법이며, 자동 결론·원인 후보는 화면에 보이지 않습니다.

## 원인을 찾는 방법 (실무 3단계)
1. **① 몫 나누기**: 실제 등락 = 시장(KOSDAQ) 몫 + 업종 몫(업종 ETF) + 종목 고유 몫.
   고유 몫이 평소의 2배 이상이면 '회사만의 이유가 있는 움직임'으로 봅니다.
2. **② 기사·공시 관찰**: `EVENT_STUDY = False`이므로 기사별 사건연구/유의성 판정은 비활성입니다.
   뉴스 반응은 관측 수익률과 단순 KOSDAQ 대비 차이(%p)를 보여줍니다. 모형 기반 예상 대비 차이와 구분합니다.
   사건 상세에서 당일·전후 5/20거래일, 연결 기사·공시, AI 해석과 사후 검토 기록을 확인합니다.
3. **③ 수급**: 거래량이 평소의 몇 배인지, 같은 증권사 창구가 업종 종목을 묶어 샀는지, 외국인·기관 순매수.

시장·업종 몫은 과거 관계에 기반한 모형 추정치입니다. 비교 자료 누락은 0 영향으로 계산하지 않습니다.
‘평소 드문 정도’는 표시된 표본/방식(경험적 순위 또는 모형 가정)의 참고값이며 기사 원인 확률이 아닙니다.

## 자료 출처
- 시세·거래원·투자자별 매매·종목 뉴스: 네이버 증권 공개 화면 데이터
- 국제·정치·업종 이슈 기사: 구글 뉴스 (한국 언론 + 영어권 주요 언론만).
  같은 내용의 한국어 기사가 있으면 영어 기사 대신 한국어 기사를 보여줍니다.

## 알림
급등·급락(±10% 이상)이 생기면 GitHub 휴대폰 앱으로 푸시 알림이 옵니다.
GitHub 설정 → Notifications에서 이메일을 켜면 같은 알림이 메일로도 옵니다 (받을 주소는 Settings → Emails에 등록한 주소 중에서 고름).
알림에는 시세 변동만 적히고, 원인은 사이트에서 확인합니다.

## 백업
- 1시간마다: 릴리스 '최신 백업'(`latest-backup`)에 최신 기록 하나 (덮어씀)
- 7일마다: 릴리스 '주간 백업'에 날짜별 파일 (`monitor-YYYY-MM-DD.db.enc`), 26주 보관
- 백업은 지운 자리를 비우고(VACUUM INTO) xz로 압축한 뒤 암호화합니다. 실행 화면 요약에 백업 크기와 표별 크기가 나옵니다.
모두 `DATA_KEY`로 암호화되어 있어 이 값을 잃으면 열 수 없습니다.

## 사이트에서 하는 일
- 분석 요청: 기준에 안 걸린 날(예: ±2.5%)도 이벤트 기록 화면의 [분석 요청]에서 날짜(필요하면 시간대)를 고르면,
  같은 방식으로 원인을 분석해 '요청'으로 기록합니다.
- 기사 직접 등록·목록에서 빼기: 버튼을 누르면 GitHub 요청 화면이 열리고, [Create]를 누르면 몇 분 안에 반영됩니다.
  요청 내용은 암호화되어 있어 다른 사람은 알아볼 수 없습니다.

## 알아두실 점
- 원인 분석은 시간상·시장상 연관성에 근거한 추정입니다. "이 때문에 올랐다"는 확정이 아닙니다.
- 공개 자료의 형식이 바뀌면 일부 수집이 멈출 수 있습니다. 실행 화면의 점검 표시로 확인합니다.

## 일별 이벤트 연구와 검증

기사·공시 상세의 근거 영역에 '평소 예상과 비교'를 추가했습니다.
기사 공개 전 자료로 평소 시장과의 관계를 추정하고, 비교 종목 기록이 충분하고 계수를 구분할 수 있으면 비교 종목 평균도 함께 반영합니다.
추정에는 기본 120거래일을 사용하며 반응일 직전 10거래일은 제외합니다. 기록은 최소 50거래일이 필요합니다.

- 예상보다 더 움직인 부분(AR) = 실제 수익률 − 평소 관계로 예상한 수익률.
- 여러 날의 합계(CAR)는 각 날의 AR을 더합니다. 복리 투자 수익률과는 다릅니다.
- 공개 전 5거래일, 반응일, 전후 3거래일, 반응일부터 3거래일, 다음 날부터 3거래일을 미리 정해 표시합니다.
- 계수 추정 오차를 포함한 표준오차와 Student t 분포로 양측 p값·95% 범위를 계산합니다.
- 필요한 시세가 없거나 미래 구간이 끝나지 않으면 해당 구간을 줄여 계산하지 않습니다.
- 종목 시세가 누락된 날을 건너뛰어 며칠 수익률을 하루 수익률로 취급하지 않습니다.

이 계산은 일별 종가 기준이므로 장중 기사 공개 전의 당일 움직임도 포함합니다. 표시는 기사 원인의 확정이나 주가 예측이 아닙니다.
오차의 독립성·일정한 분산·정규성을 가정하며 여러 구간의 p값은 다중 검정 보정 전입니다.
BMP·순위 검정·종목 간 상관 보정·GARCH·점프 검정은 이번 수정에 구현하지 않았습니다.
기사·공시 목록, 상세의 대표 수치와 판정, 보도자료·외부 기사·공시 평균 요약을 이 사건연구 결과에 연결했습니다.
평균 요약은 같은 반응일을 한 번만 세며, 새 모델로 계산한 반응일만 포함합니다. 계산·미계산 개수를 구분하고 표본 수에 맞는 정확한 Student-t 임계값을 사용합니다.
평균 차이의 범위는 서로 다른 반응일을 독립으로 가정한 단순 집계입니다. 발표일 선택 편향·다른 소식·기간 간 의존성이 있어 PR 인과 효과의 신뢰구간은 아닙니다.
정적 배포 직전에 기사·공시 모든 목록과 상세의 대표 값·판정이 일치하고 새 모델과 같은지 검사합니다. 불일치나 재계산 실패 시 기존 계산값으로 배포하지 않습니다.
당일 종가가 확정되었는지, 주식 분할 등으로 가격 기준이 바뀌었는지, 비교 종목 구성과 기사 수집이 완전한지는 별도로 확인해야 합니다.

### 기존 데이터로 시간순 점검

```powershell
python -m pip install -r requirements.txt
python validate_event_study.py --db "기존 monitor.db 경로" --symbol "종목코드" --from 2026-01-01 --to 2026-10-22
python -m pytest tests -q
node --check web/app.js
```

검증 도구는 데이터베이스를 읽기 전용으로 열고, 기사·공시·직접 등록 PR의 반응일 전후 5거래일을 제외한 후보일을 검사합니다.
각 후보일의 이전 자료만으로 다시 추정하며, 기존의 단순한 정규분포 근사와 수정한 검정의 이상 반응 판정 비율을 비교합니다.
검증 도구는 시장 모형으로 고정하므로 비교 종목을 추가한 화면 모형과는 범위를 구분해야 합니다.
수집하지 못한 사건이 남아 있을 수 있어 이 비율을 실제 오탐률이나 정확도라고 부르지 않습니다.
반응이 없을 때 덜 잘못 잡는지뿐 아니라, 실제 중요한 발표 반응을 놓치지 않는지도 별도 표본으로 확인해야 합니다.

근거: [Brown·Warner(1985)](https://doi.org/10.1016/0304-405X(85)90042-X),
[MacKinlay(1997)](https://www.bu.edu/econ/files/2011/01/MacKinlay-1996-Event-Studies-in-Economics-and-Finance.pdf).
분봉 분석의 검정 성능이나 PR 인과관계가 이 일별 모형만으로 보장되지는 않습니다.

## 사건 관찰 DB (2026-10-29)

뉴스 반응의 행·선을 누르면 그 줄 바로 아래에 기사별 관찰 기록이 펼쳐집니다(주소 `#/react/event/ne-…`, 같은 줄을 다시 누르거나 [닫기]로 접음). 순서: 제목·상태 → 당일/전후 5·20거래일 그래프와 수치 → 관련 소식·시장 상황 → 검토 기록(확인 사실/AI 분석/사후 검토) → 유사 사건 → 분류·연결 수정(접힘). 기존 필터·평균·중앙값·방향 집계·원문 상세는 유지합니다.

- 기사 묶음: 기존과 같습니다. 제목이 비슷한 같은 소식(72시간 이내)과 사이트에서 직접 합친 기사는 한 묶음, 같은 반응일의 기사는 목록·통계에서 한 사건으로 셉니다. 사건 관찰 기록의 사건 ID는 직접 연결·분리 기록으로 관리합니다. 자동 '회사 발표'(`company`) 기사는 기존과 같이 보도자료로 분류·집계합니다. 기사 분류는 당사 보도자료/외부기사/공시 세 가지입니다. 외부 기업의 발표를 다룬 기사도 외부기사이며, 이전에 저장된 `external_company_announcement` 값은 DB·이력에 그대로 두고 화면·필터·집계에서 외부기사로 읽습니다(`legacy_event_kind`로 원래 값 표시). 상세에서 분류, 복수 태그, 발표 주체·파트너·시각을 수정합니다.
- 시각: 공개, PR 실제 배포, 분석 기준, 반응 시작, 기준가격 실제 시각을 분리합니다. KST. `observatory-2-before-publication`은 장중 공개 **직전** 완료된 마지막 시세를 쓰며 한 봉 간격보다 오래되면 미집계입니다. 5/60분봉은 시작+봉 간격이 완료 시각입니다. +30/+60분 끝 가격은 정확히 일치해야 합니다. 15:00 초과 공개는 다음 **관측된 거래일** 09:00부터 비교합니다. 거래정지/수집 누락을 임의로 구별하지 않습니다.
- 비교: 주가·KOSDAQ 각각 관측 수익률(%), 같은 기준·종료 시각이 확보된 경우 단순 차이(%p). 그림·표·CSV는 동일 payload. 통계적 인과 효과 제거가 아닙니다.
- 전후 5/20거래일: 저장된 시장 거래일 달력, 반응 직전 거래일의 저장 `close`로 정규화한 가격비율. 미래는 진행 중. 일봉에는 장후 체결이 포함될 수 있고 기업행동 보정 여부도 검증되지 않았으므로 **정규장 확정 종가 비교로 오인하지 않도록 경고**합니다. CAR 합계가 아닙니다. 원천 거래일 자체가 모두 누락되면 실제 거래일 수와 다를 수 있습니다.
- 누락 그래프: 실선 중단, 60분 이내의 시각적 연결만 짧은 점선. 점선은 계산·CSV에서 제외. 출처 변경·큰 공백은 연결하지 않습니다. 평균은 각 실제 공통 관측 시각에 중복 제거 2사건 이상일 때만 표시; 점/연결선에 n과 해상도 안내. 시장 비교선(긴 대시)과 누락 연결선(짧은 점선)은 다릅니다. 1사건 평균은 표시하지 않습니다. 충돌 값은 제외하고 로그로 확인합니다.
- 기록: 질문 복사 → 외부 AI에서 검토 → 결과 붙여넣기 → GitHub 새 이슈의 Create → 다음 자동 실행. GitHub 요청은 기존 AES-GCM 경로로 암호화합니다. 기록/수정은 덮어쓰기 없이 원문·스냅샷·작성 주체·분석 시각·출처·주관적 신뢰도·사후 상태를 보관합니다. 로컬 서버는 `/api/inbox`로 즉시 반영합니다.
- 탐색: 태그·종류·발표 주체·파트너/키워드·기간·시간대·원천·부호·품질·메모 필터. 관측 CSV와 원문 목록 CSV는 별도이며, 메모/비밀키는 포함하지 않습니다. 사용자가 내려받은 CSV는 로컬에서 보호해야 합니다.

### 마이그레이션·복구

`init_db()`/관찰 build가 `news_events`, `news_event_members`, `news_event_aliases`, `news_event_history`, `news_event_notes`, `news_event_observations`, `news_event_records`, `news_calculation_migrations`를 `CREATE IF NOT EXISTS`로 추가합니다. 기존 기사·공시·시세·수동 분석은 삭제/재작성하지 않습니다. 원문 ID 연결은 대표 제목 변경에도 유지되며 명시적 연결의 이전 ID는 별칭으로 유지됩니다. 분리는 새 ID와 양쪽 이력을 만듭니다. 기존 메모는 원 사건에 남습니다.

변경된 계산 결과는 값이 바뀔 때만 새 스냅샷으로 저장됩니다. 새 계산 첫 빌드에서 기존 `reactions` 캐시가 있으면 `news_calculation_migrations`에 보존합니다. 암호화된 SQLite 백업에 모두 포함됩니다. 숨겨진/수집 목록에서 빠진 원문의 사건 링크는 마지막 관찰 기록으로 유지합니다.

배포 전 기존 암호화 최신/주간 백업을 보존합니다. 코드 롤백은 이전 커밋으로 돌아가면 되고, 추가 테이블은 그대로 두세요(삭제 불필요). 데이터 자체 복구는 기존 `DATA_KEY`와 복구 절차를 사용하되 복구 후 새로 쌓인 메모가 사라지지 않도록 현재 백업도 별도 보존하세요. `DATA_KEY`/`SITE_PASSWORD`는 바꾸지 않습니다. 운영 DB 레코드 건수 검증은 권한 있는 환경에서 수행하며 PR 테스트는 가상 DB로 멱등성·기존 건수 보존을 검증합니다.

상세 파일은 `observation:<event_id>`별 암호화 `.bin`으로 분리해 선택할 때 로딩합니다. 처음에는 요약 인덱스만 가져옵니다. 이 기능의 배포 대상은 현재 GitHub Pages 경로입니다. 레거시 Cloudflare 게시기는 신규 관찰 자료 export를 제공하지 않으며 기존 동작을 유지합니다.

검증 및 한계: [docs/observatory-validation.md](docs/observatory-validation.md). PR 단계에서는 운영 배포를 변경하지 않습니다.
